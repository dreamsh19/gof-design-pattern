- 구조 패턴은 서로 유사한 경우가 많아서, 패턴의 의도를 헷갈리기 쉬움.
- 따라서 Discussion 파트에서는 패턴 간 비교를 다룸
- 그리고 당연하게도 여러 개의 패턴을 동시에 hybrid 형태로 사용이 가능하며, 흔한 경우임.

## Adapter vs Bridge
- 유사점
	- 다른 인터페이스로 요청을 포워딩한다는 공통점이 있음
- 차이점 : 목적이 다름
	- Adapter는 기존에 존재하는 서로 호환되지 않는 인터페이스간 호환성을 위한 목적
		- 연결되는 인터페이스가 어떻게 구현 및 설계되었는지는 관심이 없음.
	- Bridge는 확장성클라이언트에게 일관된 인터페이스를 제공하면서 확장성을 확보하기 위한 목적
		- 뒤의 구현이 어떻게 추가/변경되더라도 클라이언트는 변경이 필요하지 않다.
	- 소프트웨어 개발주기 상에서 활용되는 시점이 다르다.
		- Adapter는 이미 설계된 두개의 인터페이스를 "사후적으로" 대응하기 위해 사용
		- Bridge는 "사전에" 독립적인 확장을 설계하기 위해 사용

## Composite vs Decorator vs Proxy
- composite vs decorator
	- 유사점
		- 재귀적 조합을 통해 무한의 레벨을 가질 수 있음.
	- 차이점 : 목적이 다름
		- decorator는 서브클래싱 없이 기능을 추가할 수 있게 하는게 목적임. (embellishment가 목적)
			- 클래스 폭발문제를 회피
		- composite 패턴은 여러개의 객체를 하나인 것과 "uniform"하게 처리할 수 있도록 하는 게 목적임. (representation이 목적)
- decorator vs proxy
	- 유사점
		- 두 패턴은 객체에게 간접 계층을 추가한다는 점에서 유사하며,
		- 두 패턴 모두 요청을 포워딩할 원본 객체에 대한 참조를 가지고 있음.
		- 두 패턴 모두 클라이언트에게 원본 객체와 동일한 인터페이스를 제공함(원본 객체와 구분 불가능하게 함)
	- 차이점
		- 프록시는 동적으로 기능을 추가/제거하는 것에는 관심이 없음. 그리고 재귀적 구성을 위한 디자인도 아님.
		- 프록시는 전체 기능 셋을 정의해두고, proxy가 이 기능들을 앞에서 제어함. (기능이 컴파일 타임에 static하게 정의됨.)
		- 그러나 decorator는 아주 적은 수의 기능 셋만 정의해두고, decorator를 통해 기능을 완성시켜나감. (기능이 런타임에 완성됨. static하게 전체 기능을 정의하기 어려운 경우 사용)
